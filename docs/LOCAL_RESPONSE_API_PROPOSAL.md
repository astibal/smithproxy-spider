# Native local-response design and implementation

Status: approved and implemented for native HTTP/1 and HTTP/2 flow callbacks.
The compatibility adapter uses this API; it does not own either protocol's
wire encoder.

## Problem

An HTTP addon may replace `flow.response` from its request hook. Spider can
model that value today, but the current native callback can only publish bytes
in the observed direction. Returning raw reverse bytes from the compatibility
adapter would bypass HTTP/2 HPACK state, stream flow control, cancellation and
the native lifecycle. That would be compatibility-shaped glue, not a safe
transport implementation.

## Proposed native boundary

Add one protocol-owned local-response operation to the existing connection
transaction. Its input is transport-neutral data:

- the complete request message selected as the response target;
- a status code and reason phrase;
- ordered byte header fields, including duplicates;
- a byte body;
- ordered byte trailer fields, including duplicates.

The operation stages a decision. It does not immediately write to a socket.
The existing message commit publishes the decision atomically: suppress the
retained request in the forward direction and publish the encoded response in
the reverse direction. Failure leaves both directions unchanged.

The public native API exposes one explicit staging method:

```python
api.message.respond(
    status=403,
    headers=[(b"content-type", b"text/plain")],
    body=b"blocked",
    trailers=[],
    reason="Forbidden",  # HTTP/1 only
)
```

It does not expose mitmproxy objects or a compatibility-specific name. Native
Spider scripts use the same helper. H1 publishes with `message.commit()`; H2
publishes with `message.translate()`.

## Protocol ownership

HTTP/1 owns start-line encoding, Content-Length or chunked framing, trailers,
bodyless status rules and persistence of the connection. The operation is
available only while the complete request is still retained and no request
bytes have been published upstream.

HTTP/2 owns HPACK encoding, END_STREAM placement, stream state, output windows,
queued DATA, trailer HEADERS, cancellation and the reverse-direction scheduler.
The operation must use the existing Translate state and content-reverse
capability. The adapter must never construct or inject HTTP/2 frames itself.

## Existing primitives and minimal extension

The current implementation already owns most of the transport mechanism needed
by this operation:

- Translate control state contains both directional flow-control ledgers and
  bounded output queues.
- `replacement_reverse` publishes protocol-owned bytes through the negotiated
  `content-reverse` webhook capability.
- `peer_held_parts` lets one callback atomically update a retained checkpoint
  from the opposite direction.
- The native flow instance serializes read, worker execution and publication,
  and validates both state and hold quotas before replacing the stored instance.
- Complete-message body and trailer edits already use output-only H2 units, so
  generated bytes do not invent source input ownership or WINDOW_UPDATE debt.

The implemented H2 extension gives the serialized transaction private access
to the peer-direction HPACK checkpoint. A request-side callback can therefore
encode reverse response HEADERS against the exact table already visible to the
client without exposing that checkpoint to scripts.

The minimal native extension is a peer-direction translate checkpoint in the
worker envelope. The worker privately clones the peer output encoder, encodes
the staged response, and returns the updated peer checkpoint alongside the
current checkpoint and reverse bytes. The C++ instance owner validates both
checkpoints and publishes both, the shared control state, both holds and both
directional outputs in the same serialized transaction. Failure publishes none
of them. A missing peer checkpoint means a fresh encoder only when that
direction has never emitted a header block; it must never silently reset an
existing table.

HTTP/1 uses a bounded native response-order checkpoint. Each forwarded request
owns an origin slot; a local response behind it remains queued until that
origin response is published. The queue is data-only, charged to the flow
instance quota and updated atomically with the replacement. A later local
response therefore cannot overtake an earlier origin response. Scripts never
receive an arbitrary reverse-byte primitive.

The worker also advances this checkpoint for ordinary H1 pass-through callbacks,
including native scripts that return `None`. If an origin response exposes a
previously queued local response, the worker switches that callback to the
normal native commit path and inserts the local response atomically. A raw
replacement is rejected at that boundary because its message ordering cannot
be proven.

No Smithproxy change is required for this design: the existing negotiated
`content-reverse` capability carries both the H2 and H1 reverse output. The work
is confined to Spider's native API, transaction envelope, protocol-owned
serialization, compatibility mapping and tests.

## Safety and quotas

- Require one complete, unambiguous request and a live native transaction.
- Reject CONNECT, upgrades and an already published request.
- Preserve ordered duplicate headers and trailers.
- Repair Content-Length and reject forbidden connection-specific H2 fields.
- Apply the existing bounded body and pending-output quotas.
- Reject a second terminal decision for the same exchange.
- Keep the generation failed after an action cannot be published atomically.

## Compatibility mapping

The addon adapter translates a request-hook `flow.response` assignment to
this operation after the hook completes. The facade remains responsible only
for validating the addon object model. Native code remains solely responsible
for suppressing the request and producing wire bytes.

This primitive also provides the correct foundation for reference-like
HTTP/2 reset and GOAWAY fallback responses. It does not implement kill,
destination rerouting, replay or streaming.

## Evidence and remaining release work

- HTTP/1.0 and HTTP/1.1 fixed responses, HTTP/1.1 chunked responses and
  complete trailers are covered;
- ordered duplicate headers, explicit reason phrases, 204 bodies and framing
  repair are covered;
- sequential and annotated-pipelined HTTP/1 requests are covered, including a
  local response queued behind an origin response and interleaving multiple
  origin responses in one callback;
- fragmented HTTP/2 requests with and without retained bodies;
- multiplexed streams where only one receives a local response;
- HPACK dynamic-table continuity in both directions;
- blocked and resumed HTTP/2 output windows;
- reset and GOAWAY races before and after staging;
- atomic failure under quota, validation and worker termination;
- the H1 packaged-worker lifecycle and application-owned response fields match
  the checked-in mitmproxy 12.3.1 corpus;
- the multiplexed H2 lifecycle and message semantics match the four-stream
  mitmproxy 12.3.1 corpus, including response-hook mutations, explicit 204
  bodies, duplicate trailers and stream termination. Frame segmentation is not
  compared because it is not a message-level contract;
- every request byte boundary and a 150 KiB flow-controlled local response
  beside a smaller multiplexed stream are covered. Spider intentionally
  emits a complete valid chunked
  response where the recorded reference leaves its explicit chunked-trailer
  response incomplete.
